# ClaimGuard

## Beginner's Product, Technology and Handover Handbook

**Version:** Pilot v1.4  
**Prepared:** 17 July 2026  
**Audience:** Clients, claims handlers, junior developers, testers and future maintainers

> This handbook explains what ClaimGuard does, why it exists, how a user moves through it, how the code works, where information is stored and how to run or explain the project. You do not need previous insurance or programming knowledge.

# 1. ClaimGuard in plain English

ClaimGuard is an invoice-checking assistant for UK motor insurance claims.

A garage sends a repair invoice. ClaimGuard reads the invoice, checks the arithmetic, translates garage descriptions into standard repair items, compares prices with governed evidence and highlights lines that may be overpriced. A human claims handler reviews the evidence and decides whether to challenge each line.

ClaimGuard recommends. The human handler decides.

## The problem it solves

Garage invoices are difficult to review consistently:

- Descriptions vary between repairers.
- One invoice may contain parts, labour, fees, MOT and VAT.
- A handler may need to compare many historic invoices.
- Supporting evidence must be traceable.
- The final amount must be correct to the penny.
- An insurer must later explain who decided what and why.

ClaimGuard turns a messy document into a structured, reviewable case.

## The result in one example

| Figure | Meaning | Pilot example |
| --- | --- | ---: |
| Original net invoice | What the repairer billed before VAT | £643.26 |
| Challenge Price | Evidence-backed net amount proposed for payment | £546.51 |
| Net Challenge Amount | Amount proposed for dispute | £96.75 |
| VAT impact | VAT associated with the challenged amount | £19.35 |
| Gross cash effect | Net challenge plus VAT impact | £116.10 |

MOT is shown for context but remains outside the VAT calculation.

## A one-minute explanation

> ClaimGuard is a React and FastAPI application for reviewing UK motor repair invoices. It reads every PDF page, extracts invoice lines, checks the maths, maps garage wording to a governed repair-item bank and compares each net line total with approved and historical evidence. It applies versioned £5 and 5% challenge rules, but a claims handler must approve every consequential decision. SQLite stores the complete case and audit history. The system can generate JSON, Excel, SQLite, DOCX and PDF outputs. AI is optional and constrained to mapping assistance; all money calculations are deterministic Python Decimal code.

# 2. People, inputs and outputs

## Primary user

The main user is a claims handler working for an insurer. The handler must answer:

1. Is the claim and invoice information consistent?
2. Are the extracted invoice values correct?
3. Which repair items do the invoice descriptions represent?
4. Are any prices unsupported or too high?
5. What should be challenged?
6. What evidence supports the challenge?

# 3. Important words

## Invoice Price

The quantity-adjusted net amount charged on the current invoice line.

Example: four spark plugs at £8.55 each have an Invoice Price of £34.20 net.

## Ontology

An ontology is ClaimGuard's governed catalogue of standard repair items. It lets different garage descriptions mean the same thing.

| Garage wording | Standard ontology item |
| --- | --- |
| Air Filter | Air filter (engine) |
| Pollen Filter | Cabin / pollen filter |
| Oil Service Labour | Full-service labour |

Each ontology item can have synonyms, part numbers, a unit, price observations, approval status and version history.

## Mapping

Mapping connects an invoice line to an ontology item.

Example:

```text
Invoice line: Air Filter
Mapped item:  Air filter (engine)
Relationship: 1 invoice line to 1 standard item
Confidence:   98%
Status:       Waiting for handler review
```

Mapping confidence measures how strongly the wording or part number matches. It does not measure price fairness.

## Historical evidence

Eligible observations from previous repair and service invoices. ClaimGuard uses a recency-weighted median, so newer comparable observations generally have more influence than older observations.

## Benchmark

The supported net amount calculated from reliable evidence.

Default policy when both evidence sources are reliable:

```text
Benchmark = 60% approved ontology amount
          + 40% historical weighted median
```

If one source is missing or unreliable, versioned fallback rules decide whether the remaining source may be used. If neither source is reliable, ClaimGuard does not invent a price.

## Challenge Price

The evidence-backed net amount the insurer proposes to pay.

"Proposed payable" may appear as explanatory text, but Challenge Price is the fixed product term.

## Net Challenge Amount

The net amount proposed for dispute:

```text
Net Challenge Amount = Invoice Price - Challenge Price
```

It is positive-only. A cheaper invoice line never reduces or offsets challenges on other lines.

## Challenge Score

A score from 0 to 100 describing evidence strength and defensibility. It is not money and is separate from the size of the overcharge.

## Provisional

Evidence or a mapping that has not yet received the required human approval. Provisional evidence may help preview a case but cannot enter an issued negotiation letter.

# 4. The complete user journey

## Simple flow

```text
Create claim
    |
Confirm claim and liability
    |
Upload invoice PDF
    |
Classify and extract every page
    |
Review extracted values and calculations
    |
Map invoice lines to standard items
    |
Compare prices with governed evidence
    |
Handler accepts, edits or rejects findings
    |
Approve and generate challenge package
    |
Record eventual settlement
```

Every step is persisted. The handler can leave and reopen the case.

## Step 1: Create and understand the claim

The claim stores the parties, vehicles, accident information, damage description and invoice context.

The invoice does not establish legal fault. ClaimGuard may flag inconsistencies, but only a human handler confirms liability.

Allowed liability states are:

- Admitted
- Denied
- Split liability
- Pending
- Human review required

Draft invoice analysis can continue while liability is pending. Final challenge issue is allowed only when the liability gate is satisfied, normally human-confirmed Admitted or Split Liability.

## Step 2: Upload the invoice

The API validates:

- File extension and PDF signature
- Upload-size limit
- Maximum page count
- Safe storage name
- Duplicate document hash where relevant

Invalid files fail closed rather than entering the extraction pipeline.

## Step 3: Read every page

The PDF pipeline uses a native-first strategy:

1. Read embedded text and tables with PyMuPDF and pdfplumber.
2. Render and OCR image-only or poor-quality pages with Pillow and Tesseract.
3. Detect rotation and repair page orientation where possible.
4. Classify each page as invoice, estimate/order or other.
5. Group related pages without silently merging separate invoices.

A failure on one page is isolated and presented for review instead of destroying the entire job.

## Step 4: Extract invoice facts

The pipeline extracts:

- Supplier, customer and vehicle details
- Invoice number and date
- Parts, labour, subtotal, VAT, MOT and gross totals
- Individual line descriptions
- Quantity, unit, unit price and line total
- Extraction method and confidence
- Source page, raw text and bounding box when available

The source information is important because a reviewer must be able to trace a displayed value back to the original document.

## Step 5: Check calculations

Deterministic rules verify relationships such as:

```text
quantity x unit price = net line total
parts + labour = taxable subtotal
taxable subtotal x VAT rate = VAT amount
taxable subtotal + VAT + non-VAT items = gross total
```

Small rounding tolerances are explicit. MOT is treated outside VAT.

## Step 6: Map invoice descriptions

Candidate retrieval follows this order:

1. Exact part-number match
2. Exact canonical-name match
3. Exact synonym match
4. Bounded fuzzy-text match

Only type-compatible candidates are retained. For example, a labour line should not silently map to a part.

An optional Gemini model may choose one item from the retrieved candidate list or return no match. It cannot invent an ontology ID and cannot perform financial calculations. Without an API key, deterministic retrieval still works.

## Step 7: Compare prices

ClaimGuard converts evidence into comparable net line totals. It multiplies unit prices only when unit and quantity are explicit and compatible. Unknown or incompatible quantity information is sent to review instead of being guessed.

The default v1.4 policy uses:

- 60% approved ontology evidence
- 40% eligible historical weighted median
- Minimum three eligible historical observations
- Recency half-life of 365.25 days
- Positive difference of at least £5
- Positive difference of at least 5%

Both the £5 and 5% gates must pass.

## Step 8: Review findings

For each challenged line, the handler sees:

- Repairer-billed amount
- Evidence-supported amount
- Potential net challenge
- Mapping and evidence confidence
- Ontology and historical evidence
- Policy rule and reason

The handler can accept the Challenge Price, adjust it with a rationale or choose not to challenge.

## Step 9: Finalise

Finalisation checks that:

- The current comparison run is complete.
- Liability is human-confirmed and allows issue.
- Every positive challenge line has an approved or rejected decision.
- Issued values use approved, traceable evidence.

The final invoice summary is recalculated from human-approved line decisions. The case is then marked finalised and an audit event is written.

## Step 10: Record settlement

The final agreed net amount is recorded at invoice level. A line-level allocation is optional. Settlement observations can later improve the historical evidence bank.

# 5. Worked example: Air Filter

Suppose the garage invoice contains:

```text
Description: Air Filter
Quantity:    1 each
Net total:   £20.02
```

## Mapping

ClaimGuard normalises the wording and finds the ontology item `Air filter (engine)`. The wording match may show 98% confidence. This only means the item identity is likely correct.

## Price comparison

Eligible evidence supports £13.27 net for the comparable line total.

```text
Invoice Price       £20.02
Challenge Price     £13.27
Net Challenge        £6.75
```

Calculation:

```text
£20.02 - £13.27 = £6.75
```

The difference is above £5 and above 5%, so the line passes both policy gates. The handler still decides whether to accept, edit or reject the proposed challenge.

If a line shows `Net challenge £0.00`, either the billed amount is supported, the difference failed one of the gates or reliable evidence is unavailable. In that situation the Challenge Price remains the full billed net amount.

# 6. The interface and user experience

## Main navigation

The everyday handler journey is intentionally short:

| Main screen | Question answered |
| --- | --- |
| Overview | What happened and what must I do next? |
| Documents | What was uploaded and extracted? |
| Review findings | Which proposed challenges should I accept, edit or reject? |
| Approve challenge | Are the final figures and outputs ready? |

Specialist screens remain under Administration:

- Document pages
- Extracted invoice
- Calculation checks
- Ontology mapping
- Missing-item research
- Ontology bank
- Audit and reports

No feature is removed. Less-frequent technical detail is moved away from the primary journey.

## UX principles used

### One primary action

Each main screen should make the next action obvious. Examples are Review challenged lines and Generate challenge package.

### Progressive disclosure

The main view uses handler language and summary values. Technical identifiers, evidence provenance and detailed calculations appear in sheets, dialogs or Administration screens.

### Table-first work surfaces

Dense, repeated records such as invoice lines and mappings use tables because tables make row-by-row comparison easier. Secondary details open without losing the current case context.

### Restrained status colour

Colour communicates state rather than decoration:

- Green: confirmed or completed
- Amber: review required
- Red: eligible high-impact challenge or blocking error
- Neutral grey: information, inactive or below threshold

Text labels remain present so meaning does not depend on colour alone.

### Consistent components

The interface uses shadcn and Radix primitives for buttons, cards, tables, dialogs, sheets, badges, alerts, tabs and form controls. Tailwind CSS provides shared spacing, typography and colour tokens. Lucide supplies a minimal icon set.

### Human control

Consequential actions require a clear user decision and rationale. AI suggestions and human decisions are stored separately.

### Safe demo fallback

If the API is unavailable, the frontend loads an explicitly labelled demo workspace. Demo mode never pretends that mapping approvals, challenge decisions or finalisation were persisted.

## Known UX boundary

The current pilot uses screen state rather than distinct routes for every view. Production work should add deep links, stronger browser history and a complete keyboard, focus, zoom and measured contrast audit.

# 7. Technology architecture

## The simplest mental model

ClaimGuard has three main parts:

```text
Browser interface
      |
      | HTTP / JSON
      v
FastAPI application
      |
      | SQLAlchemy
      v
SQLite database and stored documents
```

The browser displays information and sends user actions. FastAPI owns business operations. SQLite stores the durable record.

## Detailed data flow

```text
React screen
  -> typed API helper
  -> FastAPI route
  -> service workflow
  -> deterministic domain logic
  -> SQLAlchemy models
  -> SQLite transaction
  -> workspace/result builder
  -> JSON response
  -> React state and UI update
```

Document processing adds another branch:

```text
Uploaded PDF
  -> file validation and storage
  -> page classification
  -> native extraction or OCR
  -> invoice parser
  -> calculation validator
  -> persisted pages, invoices, lines and findings
```

## Why SQLite

SQLite is suitable for this trusted single-machine pilot because it is simple, portable and requires no separate database server. The configuration enables foreign keys, WAL mode and busy timeouts.

For concurrent multi-user production, evaluate PostgreSQL, tenant isolation, connection pooling, backups and disaster recovery.

The backend separates responsibilities:

| Liability | Confirm human liability decision |
| Documents | Upload, process and inspect pages |

Write operations use database transactions. Successful work is committed. Validation or processing errors roll back partial changes. Reprocessing creates a new immutable run rather than overwriting the previous result.

# 9. Database mental model

The database contains many tables, but a beginner can understand them as six groups.

## Claim group

```text
Case
  -> ClaimContext
      -> ClaimParty
      -> ClaimVehicle
      -> LiabilityAssessment
      -> LiabilityEvidence
```

This group answers who, what happened, which vehicles and what the human liability decision was.

## Document group

```text
Case
  -> Document
      -> DocumentPage
      -> Invoice
          -> InvoiceLineItem
          -> MathFinding
```

This group stores the uploaded file, every page, extracted invoice and calculation findings.

## Ontology and evidence group

```text
OntologyVersion
  -> OntologyItem
      -> OntologySynonym
      -> PriceObservation
      -> VehicleApplicability

HistoricalObservation
ExternalEvidence
```

This group stores standard identities and dated evidence. New prices are appended rather than silently replacing history.

## Comparison group

```text
ProcessingRun
  -> MappingRun
      -> OntologyMapping
  -> PriceComparison
      -> ComparisonComparable
  -> ChallengeResult
```

This group records which versions produced a result, how lines mapped, which evidence rows were used and what challenge was calculated.

## Governance group

```text
ResearchTask -> ResearchItem
ReviewTask   -> ReviewDecision
Settlement
AuditEvent
```

This group stores missing-item research, human review, settlement and the audit trail.

## Version and provenance group

Configuration, source-import, ontology, policy, extraction, prompt and model versions make results reproducible. A reviewer can identify exactly which inputs and rules produced a figure.

# 10. Mapping, AI and safety boundaries

## What deterministic code does

- Normalises descriptions and part numbers
- Retrieves exact and fuzzy ontology candidates
- Checks item-type compatibility
- Checks quantity and unit compatibility
- Selects eligible historical observations
- Calculates all prices, gates, VAT and totals

## What the optional model may do

- Read a redacted invoice description
- Consider only candidates supplied by deterministic retrieval
- Select one supplied ontology ID
- Return no match
- Provide a short rationale and confidence

## What the model may not do

- Invent ontology IDs
- Create a price
- Calculate quantity, VAT or totals
- Decide liability
- Approve evidence
- Finalise a challenge

## Hosted Gemini configuration

The optional provider is `gemini-2.5-flash-lite`. The API key belongs only in `backend/.env`:

```text
CLAIM_GUARD_LLM_PROVIDER=gemini
CLAIM_GUARD_LLM_MODEL=gemini-2.5-flash-lite
CLAIM_GUARD_LLM_API_KEY=your_private_key
```

If the key is absent, health reports `configuration_required` and comparison continues deterministically. If the provider times out, rate-limits or returns invalid JSON, ClaimGuard records a safe failure code and falls back for that run.

Free-tier cloud data terms may not be suitable for real insurer data. Production use requires insurer approval, appropriate contracts, data-location review and completed DPIA work.

# 11. Financial rules

## Why Decimal is used

Binary floating-point numbers can introduce tiny errors. Insurance figures must agree to the penny, so backend money logic uses Python `Decimal` with explicit rounding.

## Quantity-adjusted line total

The monetary challenge is based on net line total, not only unit price. This catches cases where the unit price looks reasonable but the billed quantity is excessive.

## Evidence fallback

| Evidence state | Behaviour |
| --- | --- |
| Approved ontology and reliable history | 60% ontology plus 40% historical weighted median. |
| History weak or ineligible | 100% approved ontology. |
| Ontology missing or provisional | History-only when policy permits, with human review required. |
| Neither reliable | No fabricated benchmark and £0 final challenge. |

## Challenge gate

```text
raw difference = max(invoice net - benchmark net, 0)

gate passes when:
raw difference >= £5
AND
raw difference / invoice net >= 5%
```

If either condition fails, the Challenge Amount is £0.

## Severity

- Red: eligible challenge of at least £25 or at least 25%
- Amber: other eligible challenge passing £5 and 5%
- Neutral: below gate, below benchmark, unsupported or awaiting evidence

Severity is a review aid. It does not approve a decision.

# 12. Audit and reporting

## What is audited

- Uploaded file identity and hash
- Extracted values and provenance
- Page and line corrections
- Mapping candidates and decisions
- Evidence sources and comparables
- Policy and ontology versions
- Model/provider/prompt details when AI is used
- Handler approvals, edits, rejections and rationales
- Finalisation and settlement

Audit events capture actor, time, entity, event type, before/after values and event payload. New events are hash-chained to make later alteration detectable.

## Why reports are gated

Review exports such as JSON and Excel may be available before final issue. Negotiation letters are more consequential, so DOCX and PDF require the liability and challenge-review gates.

All negotiation amounts are injected from approved structured facts. The model does not write authoritative numbers into letters.

# 17. Common questions

## Can it run without an AI key?

Yes. PDF extraction, calculation checks, candidate retrieval, comparison and challenge maths are deterministic. The hosted model is optional mapping assistance.

## Can the AI decide the payable amount?

No. Python Decimal code calculates the benchmark, gates, VAT and totals. Human approval is required.

## Why are mappings marked Review when confidence is high?

High confidence means the wording likely matches. The evidence or ontology item may still be provisional, or pilot policy may require a handler decision.

## Why does the header say zero matched when rows exist?

In the current pilot this refers to zero handler-approved mappings, while the visible rows are provisional candidate mappings. A clearer label is "0 approved, 18 awaiting review."

## What happens if a price cannot be supported?

ClaimGuard returns review required or not challengeable and produces a £0 final Challenge Amount. It does not guess a price.

## Why is settlement after finalisation?

Settlement records the eventual negotiated result. It should not appear as if the insurer already agreed an amount before the challenge was reviewed and issued.

## Why is the database not included in the handover ZIP?

The schema is recreated with Alembic and demo records are created by bootstrap. Excluding runtime databases prevents accidental sharing of local claims or audit data.

## What should be sent to a new client?

- Clean source ZIP

# 19. How to explain the project confidently

Use this sequence:

1. Start with the business problem: checking garage invoices consistently.
2. Describe the user: an insurer's claims handler.
3. Explain the journey: claim, PDF, extraction, mapping, comparison, review and package.
4. Define Challenge Price: the evidence-backed net amount proposed for payment.
5. Explain human control: AI does not decide liability or calculate money.
6. Describe the architecture: React, FastAPI and SQLite.
7. Describe evidence: approved ontology plus eligible previous invoices.
8. Mention auditability: every source, rule, version and human decision is retained.
9. Finish with the boundary: complete local pilot, not yet a public insurer platform.

## Short technical explanation

> React and TypeScript provide the shadcn-based handler interface. Typed HTTP requests call FastAPI. Service modules coordinate SQLAlchemy transactions and deterministic domain functions. The PDF pipeline uses native extraction first and Tesseract OCR when needed. Mapping uses exact and fuzzy retrieval with an optional constrained Gemini adjudicator. The comparison engine uses Decimal and versioned YAML policy. SQLite stores the relational case graph and hash-chained audit events. Alembic manages schema versions, and export modules generate JSON, Excel, SQLite, DOCX and PDF artifacts.

## Short product explanation

> ClaimGuard reads repair invoices, identifies the standard repair item behind each garage description, compares the billed net line total with approved and historical evidence and shows the handler exactly what may be challenged. The handler decides every challenged line, after which ClaimGuard produces an audit-ready challenge package.

# 20. Handover checklist

Before giving the project to another person:

- Confirm the source ZIP opens successfully.
- Confirm no `.env`, API key or runtime database is included.
- Confirm sample PDFs are authorised for sharing.
- Give the recipient this handbook and the README.
- Explain that they must install Node.js, Python, uv and Tesseract.
- Ask them to run backend migration and bootstrap before starting the UI.
- Let them know Gemini is optional and requires their own key.
- Describe the build as a single-machine pilot.
- Point production questions to `SECURITY_AND_DPIA.md`.
- Keep policy changes versioned rather than editing past results silently.

## Final mental model

```text
ClaimGuard is not an automatic claims decider.

It is a governed evidence and calculation assistant:

document -> structured facts -> standard item -> price evidence
         -> deterministic recommendation -> human decision -> audit package
```

That sentence captures the entire project.
